# Pulsemon Agent Guide

This file is the starting point for coding agents working in Pulsemon. Nested
`AGENTS.md` files add local rules for specific directories.

## Product Context

Pulsemon is a Cloudflare Workers observability app for realtime systems:
voice AI, WebSocket/SSE/gRPC-style connection lifecycles, agent workflows,
logs, traces, metrics, monitors, SLOs, and OTLP ingest.

The app is intentionally operator-facing. UI work should stay dense, scannable,
and useful for repeated platform-team workflows rather than marketing-style
presentation.

## Stack

- Runtime: Cloudflare Workers, D1, Durable Objects.
- HTTP app: Hono.
- Domain logic: Effect programs with typed errors and injected dependencies.
- UI: Hono JSX SSR, `vite-ssr-components`, HTMX, Tailwind.
- Tests: Bun test with an in-memory SQLite D1 shim.
- Schema and migrations: Drizzle schema plus generated SQL D1 migrations.

## High-Level Map

- `src/index.ts`: Worker entrypoint, auth middleware, scheduled maintenance,
  monitor alert processing, and SLO evaluation.
- `src/router.ts`: route registration generated by `bun run routes`.
- `src/routes/`: Hono route handlers and page routes.
- `src/lib/effect/`: Effect services, schemas, repositories, and typed errors.
- `src/lib/`: auth, tenancy, facets, rendering, websocket search sessions.
- `src/components/`: server-rendered JSX UI components.
- `src/db/schema.ts`: Drizzle table declarations and inferred types.
- `src/sdk/`: TypeScript SDK for instrumentation clients.
- `src/test/`: test helpers and API/service/route/SDK tests.
- `migrations/`: ordered D1 SQL migrations.
- `scripts/`: operational scripts for smoke, load, restore, DR, and OTLP
  certification.
- `specs/`: implementation plans, readiness plans, and operational specs.
- `docs/`: contributor and agent-facing guides.

## Required Commands

Run these before handing off material changes:

```bash
bun run typecheck
bun test
bun run build
bun run restore:check
```

For a full local gate, use:

```bash
bun run check
```

When adding or renaming files under `src/routes`, run:

```bash
bun run routes
```

## Migration Discipline

Drizzle is the source of truth for schema migrations. The migration history was
reset before production use, so `migrations/0000_busy_quicksilver.sql` is the
generated initial schema and `migrations/meta` contains the Drizzle baseline.

For schema work:

1. Update `src/db/schema.ts`.
2. Run `bun run db:generate`.
3. Inspect the generated SQL in `migrations/`.
4. Update tests and affected repository insert/select code.
5. Run `bun run restore:check` plus the normal verification commands.

Do not hand-write migrations unless Drizzle cannot express the required D1 SQL;
if you must, document why in the migration and update Drizzle metadata with a
follow-up generated baseline.

## Coding Standards

- Use TypeScript strict types. Avoid `any` except in test shims or when wrapping
  untyped platform APIs.
- Treat `src/db/schema.ts` as the single source of truth for persisted shapes.
  Import table row types from `@/db/schema` and derive write/update contracts
  from `$inferSelect` or `$inferInsert`; do not redeclare DB row interfaces in
  service, route, or component code.
- Keep route files thin: parse request details, build dependencies, call an
  Effect service, and map typed errors to HTTP responses.
- Keep business rules in `src/lib/effect`, not in JSX components or route
  handlers.
- Use Effect errors from `src/lib/effect/errors.ts` for expected failures.
- Inject repositories/controllers through dependency objects instead of reading
  globals in services.
- Preserve tenant scope (`workspace_id`, `project_id`) in all read/write paths.
- Redact and govern telemetry before persistence.
- Prefer structured JSON parsing/serialization over ad hoc string manipulation.
- Keep D1 writes idempotent where the domain expects retryable ingest.
- Use ASCII in source and docs unless an existing file already uses non-ASCII
  for UI text.

## UI Standards

- Keep dashboards and tables compact, dark, and operator-focused.
- Use existing components and styling conventions before inventing new layout
  primitives.
- Do not nest cards inside cards.
- Keep form controls and labels compact; validate server-side in Effect
  services.
- Ensure text fits at mobile and desktop widths.

## Testing Standards

- Add focused tests next to the behavior being changed.
- Use `createTestContext` from `src/test/helpers.ts` for route/API tests.
- Service tests should exercise Effect programs directly where possible.
- For schema changes, update seed helpers and at least one ingest/readback test.
- For OTLP changes, update `src/test/fixtures/otlp.ts` and
  `src/test/api/otlp.test.ts`.
